Honey Serve GitHub push workflow
Last updated: 2026-09-17

Use this workflow for this repo. Do not switch to SSH, GitHub CLI, LFS, or a
different remote unless the user explicitly asks.

Known good direction
====================

- Repo: E:\github\badminton-elo-ranking
- Remote: https://rcheol@github.com/rcheol/elo.git
- Branch: main
- GitHub account: rcheol
- Network-safe push command (from the repo, in PowerShell):
  .\scripts\push-github.ps1
- This wraps the same HTTPS Git push with HTTP/1.1 and the existing credential
  helper. It does not commit/stage files or change the remote or credentials.
- Authentication style:
  HTTPS + Git Credential Manager + Windows Credential Manager.

Connection recovery verified on 2026-09-17
=========================================

- Direct GitHub TLS connections reset before authentication. NO_PROXY inherited
  from the machine included github.com, bypassing the configured company proxy.
- Using the existing HTTPS_PROXY for GitHub returned HTTP 200; git ls-remote
  succeeded with Windows Schannel and TLS certificate verification enabled.
- scripts/push-github.ps1 removes only github.com/.github.com from NO_PROXY for
  its Git child process, then restores the calling shell's original value in
  finally, even if push fails. User/machine environment settings are untouched.
- The helper uses Schannel with sslVerify=true for this command. It does not
  disable certificate checks or rely on the legacy global sslVerify=false.
- Connection/authentication check without updating GitHub:
  .\scripts\push-github.ps1 -DryRun
- Do not request a new token, delete stored credentials, or split commits for a
  TLS connection reset: that error happens before authentication or upload.

Rules
=====

1. Use PowerShell/Windows Git credential flow.
   - The user has repeatedly confirmed that push works from VSCode PowerShell.
   - Keep using HTTPS and Windows Credential Manager.
   - Do not try SSH; the company/network path can block GitHub SSH.
   - Do not switch to another method just because a non-interactive Codex shell
     cannot show the credential prompt. The old successful method is still the
     source of truth.

2. Do not delete or rewrite GitHub credentials casually.
   - Do not delete git:https://github.com credentials unless the user explicitly
     approves it in that moment.
   - If push fails with HTTP 403, first inspect which credential is being used:
     cmdkey /list
     "protocol=https`nhost=github.com`nusername=rcheol`n`n" | git credential fill
   - Mask any password/token output.
   - A stale credential such as User: 43690919 for git:https://github.com can
     cause 403 for rcheol/elo.

3. If authentication is missing, restore the old successful flow.
   - Open an interactive PowerShell in the user session.
   - Run:
     cd E:\github\badminton-elo-ranking
     .\scripts\push-github.ps1
   - Let Git Credential Manager open its browser/login prompt.
   - The user signs in as rcheol once.
   - After that, normal non-interactive pushes should work again because Windows
     Credential Manager has the correct credential.

4. Keep asset files small.
   - Player cards should be under 36KB when possible and always under 40KB.
   - Do not use Git LFS. The user's company environment blocks LFS.
   - For image/card work, commit and push one image file at a time. The company
     network can return HTTP 403 when one push pack is around 100KB+ even if
     every individual file is below 40KB.
   - If several small commits are already local, push them incrementally:
     git push origin <commit-sha>:refs/heads/main
     then repeat with the next commit SHA in chronological order.

5. If a non-interactive push fails with:
   fatal: helper error (-1): authentication prompt was canceled
   bash: /dev/tty: No such device or address
   then the current shell could not show the GCM prompt. Do not keep retrying
   the same non-interactive command. Use step 3.
